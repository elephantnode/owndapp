# 実装済みの機能と対応範囲

2026-10-26時点の実装。初めて使う方は[README](../README.md)と[使い方](usage.md)を参照してください。ここでは検出・読み取り・照会の詳しい挙動を説明します。将来の設計案の全項目が実装済みという意味ではありません。

- 多言語のmanifestと配置設定を使った静的な候補検出。Node.js系、Python、PHP、Go、Rustなど。
- Vue・Next.jsなどの依存宣言による構成ラベル、Lambdaなどの静的な配置設定の識別。
- AWS SAM: `template.yaml` / `template.yml` / `template.json`（`AWS::Serverless::Function` や Transform の宣言）、および `samconfig.toml`（あれば `template_file` / `template` が指すテンプレートも読む）。クラウド上のスタック実在は確認しない。`.aws-sam` のビルド成果物は探索しない。
- 明示されたworkspaceの親子候補のグルーピング。独立したネストGitは統合しない。
- Git・SAM/CloudFormationテンプレート・Flutter/Dart・Docker・WordPress・Apps Scriptのフォルダを境界とし、配下で見つかった構成を1つのプロジェクトのComponentにまとめる。ネストGitだけは別候補。直下が `.git` だけのGitリポジトリは複数のアプリの入れ物とみなし、それ自体は候補にせず中のアプリを個別の候補にする（根拠に所属リポジトリを記録）。
- WordPress本体のないバックアップ（`wp-content` を含むフォルダ、`themes`・`plugins` を直接置いたフォルダ、`plugins/index.php` のあるフォルダ）も、サイト・バックアップ単位の1件にまとめる。探索結果には、配下で別に登録済みのプロジェクト数を表示する。
- WordPressのコア（wp-includes / wp-admin）・uploads・プラグインやテーマの内部、`*.dist-info` を含むPythonライブラリの同梱先（Lambdaレイヤーなど）は探索しない。
- 新しい探索は、深さ・総件数・総時間による打ち切りをせず、進捗・処理待ち・検出根拠をSQLiteに保存する。フォルダ一覧は少量ずつ読み、候補の整理も保存しながら進める。
- 既定の生成物・取得済み依存、ユーザー指定フォルダ、symlinkの除外は維持する。探索中は確認項目・処理済み/処理待ちフォルダ・検出数を表示する。全体量は不明なので完了率を表示しない。他画面に移っても探索は続く。
- 「一時停止」「続きから再開」「失敗したフォルダを再試行」に対応。アプリ再起動時は保存済み探索を一時停止に復旧し、自動では再開しない。「保存した探索の履歴」から過去の探索も開ける。探索記録の削除は登録済みプロジェクトに影響しない。
- 候補は30件、問題は100件、履歴は20件ずつ取得する。候補の一括登録は1回2000件までで、探索件数の上限とは別。大きなプロジェクトの一覧は構成と根拠を各200件までと総数を示し、登録時は保存済みの全構成を使用する。[設計と検証記録](discovery-plan.md)を参照。
- 選択登録、重複防止、登録直前の構成再確認、検索・絞り込み、用途・タグ・状態・メモの保存。
- アーカイブ・復帰、整理履歴、別タブの編集競合の検出、未保存の入力保護。
- 明るい管理画面、システムフォント、最小限の動き、⌘Kでの検索、狭いウィンドウへの対応。
- 依存版台帳と横断検索（npm・Yarn・pnpm・Composer・Python・Rust）。「アプリを追加」で登録したプロジェクトは、登録後に自動で依存情報を読み取る（裏側で順に読み、画面に進み具合を表示）。登録済みのプロジェクトは「依存検索」の「アーカイブ以外をすべて読み取る」でまとめて読める。カタログで選んだプロジェクト（1回1000件まで）またはプロジェクト詳細から「依存情報を読む」と、プロジェクト直下と各Componentの lock を読み、パッケージ名・解決版・宣言範囲・直接/間接・本番/開発・取得元を保存する。「依存検索」でパッケージ名（部分一致が既定・完全一致へ切り替え可能・大文字小文字を区別しない）と版（任意・完全一致）から、使っているプロジェクトを探せる。
  - 読む lock：`npm-shrinkwrap.json`／`package-lock.json`（lockfileVersion 1〜3）、`yarn.lock`（v1・2以降）、`pnpm-lock.yaml`（lockfileVersion 5〜9）、`composer.lock`、`poetry.lock`、`uv.lock`、`Pipfile.lock`、`requirements*.txt`、`Cargo.lock`。1つの場所に複数ある場合はすべて読む。workspace（npm・Yarn・pnpm・uv・Cargo）のメンバーは外側の lock で読む。
  - `requirements*.txt` は `==`（`===`）で版を固定した行だけ版を記録する。範囲指定や版のない行は宣言だけを残し、照会しない（画面に「版の固定なしを含む」と件数を出す）。`-r` の参照先はたどらず、同じ場所の `requirements*.txt` をそれぞれ読む。推移的な依存は書かれていない分しかわからない。
  - Python のパッケージ名は PEP 503 の形（小文字、`_`・`.` を `-`）で記録し、検索も同じ形で一致させる。Composer の `v1.2.3` は `1.2.3` として記録する。
  - Yarn 2以降・pnpm の lock はレジストリを記録しないため、取得元は「レジストリ（lockに記録なし）」になる。Composer は Packagist の記録（`notification-url`）があるものを公開、VCS・path のリポジトリのものを Git・ローカルとして扱う。
  - pyproject.toml がツールの設定だけ（ruff など）のときは Python のプロジェクトとして扱わない。setup.py は読まない。
  - 「依存検索」の下に、記録されているパッケージを使っているプロジェクトが多い順に一覧する（直接依存として使う件数・記録された版つき）。名前の一部で絞り込め、名前を選ぶとそのパッケージで検索する。
  - lockを読むだけで、対象プロジェクトでのインストール・スクリプト実行・設定の評価はしない。読み直すとそのプロジェクトの結果を置き換える。詳細画面では、読み取り後にlockや宣言のファイル（package.json・composer.json・pyproject.toml・Pipfile・Cargo.toml）が変わったことを示す。
  - lockなし・壊れたlock・未対応の形式・宣言のファイルとの不一致・読み取れないファイル（シンボリックリンクや範囲外への参照、32MiB超）は、それぞれ区別して表示する。読めたlockと未対応形式が同居する場合は「一部を読み取れません」とし、全体を確認できたとは扱わない。lockなしの場所だけがあっても要対応には出さない（権限不足や壊れた形式など、本当に読めなかったときだけ要対応）。読み取っていないプロジェクトは検索結果に含まれず、画面に読み取り済みの件数を示す。
  - 解決版はlockに記録された版で、node_modulesの実体やデプロイ済みの版を確認したものではない。公開レジストリ（registry.npmjs.org・registry.yarnpkg.com・packagist.org・pypi.org）以外のレジストリ・URL・Git・ローカルの依存は区別して記録する。
- 対応記録（メニュー「脆弱性と対応」）。照会で見つかった既知の脆弱性を、プロジェクト×アドバイザリの単位で対応状況（未対応・調査中・対応中・再照会待ち・対象外）を記録して進める。アーカイブしたプロジェクトは一覧に出さない（対応記録は残る。詳細の対策メモではそのプロジェクトだけ参照できる）。「解消確認」は手では付けられず、再照会で検出されなくなったときに自動で付く（再び検出されたら未対応に戻る。一部しか照会できなかったときは何も変えない）。対象外には根拠が必要で、見直す日を入れられる。
  - 優先度は悪意のあるパッケージ・緊急・高を「高」、中を「中」、低を「低」、重大度不明を「要確認」とする。公開状況・管理状態・dev/間接依存という分類だけでは自動で下げない。出典・CVSS値・差異・前回情報の保持を画面とメモに示す。アーカイブは通常の対応一覧から外れるが、詳細と記録は残る。判定範囲と取り込みの制限は [重大度と優先度](severity-policy.md) を参照。
  - プロジェクトごと・アドバイザリごとに切り替えて、状態・優先度・公開状況・文字で絞り込み、まとめて状態を変更できる（1回800件ずつ送る）。
  - 詳細の上部に「プロジェクト全体の対応状況」を1か所表示する。個別記録を集約し、未対応が残る場合は未対応、全件解消を完全な再チェックで確認した場合は完了となる。一括変更はその時点の全対象を1回で保存し、通常の変更では個別メモを保持する。対象外にする場合は共通の根拠が必要。対象が変わっていた場合は変更を保存せず再確認を促す。個々の脆弱性の詳細には対応状況の変更ボタンを置かない。
  - 「対策メモ」で、未解消のものをパッケージの版ごとにまとめた Markdown を作り、コピーできる（直接依存は更新先の版、間接依存は `npm ls`・`yarn why`・`pnpm why`・`composer why`・`uv tree --invert`・`poetry show --why` などでの経路確認、依存管理方針に沿った進め方、確認していないことを含む）。
- 既知の脆弱性の照会（npm・Composer（Packagist）・Python（PyPI）・Rust（crates.io）、[OSV](https://osv.dev)）。依存を読み取ったプロジェクトを一覧で選ぶか詳細画面から「脆弱性を照会」すると、確認画面で送信先（`https://api.osv.dev`）と送る件数を示してから照会する。
  - 送るのは ecosystem・パッケージ名・版だけ。npm・Composer・Pythonは公開レジストリと別のレジストリ（ミラー・社内のインデックスなど）由来の依存が対象。Rustは公開crates.io由来を確認できた依存だけが対象で、パス・プロジェクト名・ソース・Git/URL/ローカルの依存は送らない。同じ版は1回だけ照会する。
  - 結果は照会したときの依存台帳に結びつけて保存する。アドバイザリのID・別名・概要・重大度（発行元のラベル、対応するCVSS、悪意のあるパッケージ）・該当範囲の修正版（アドバイザリに記載がある場合）を、一覧・詳細・カタログ上部に表示する。取り下げられたアドバイザリと、別名による重複は数えない。
  - 一度に1000件まで選べる（フォルダ別表示のフォルダのチェックでまとめて選べる）。照会は裏側で進み、画面上部に「依存を読み取り中 → OSVに照会中 → 詳細を取得中」の進み具合を出す。照会の前に、依存を未読み取りのもの・前回lockがなかったり一部しか読めなかったもの・読み取り後にlockが変わったものを読み直し、判定できるものはすべて判定する。lockがないなど判定できないものは「判定できる依存なし」と示し、「脆弱性なし」とは記録しない。
  - OSVへは500件ずつ順に送り、詳細は8件ずつ並行して取得する。混雑（429）・サーバーエラー・応答なしは、`Retry-After` があればそれに従い、なければ1秒・2秒・4秒・8秒と待って再試行する（最大4回）。
  - 照会に失敗した分は「0件」にせず、前回の結果を残す。照会後に依存内容・検査範囲が変わると「再チェックが必要」と表示する。同じ内容を読み直しただけでは前回の結果を維持し、照会日時は更新しない。古い記録は照会時の内容を特定できる場合だけ引き継ぐ。既知の脆弱性があるプロジェクトは「要対応」に入る。
  - OSVに登録済みの既知の脆弱性だけが対象で、実際に悪用できるか・未公開の問題がないかはわからない。
- Git情報の読み取り（詳細画面、カタログで選んで「Git情報を読む」、またはカタログの「Gitをすべて読む」でアーカイブ以外を一括）。プロジェクト直上または祖先の `.git`（worktree の `gitdir:` 含む）から、現在ブランチ（または detached）と remote 名／URL を読む。URL の認証情報は保存前に除く。fetch・pull・`git status`（未コミットや追跡先との差）はしない。読み取りはこのMacの中だけで、外部には送らない。一括は裏側で進み、画面上部に進み具合を出す。

「依存検索」の「依存の検索範囲」で、未読・未対応形式・一部読取失敗・lockなしのアプリを確認できる。名前・パスで絞り、表示中のアプリだけを選んで依存情報を読み直す。アーカイブは「アーカイブも含める」を選ぶと対象にできる。読み直すと検索結果と記録パッケージを更新する。

Rustの取り込み・検索対象と未対応範囲は [依存解析の対応範囲](dependency-coverage.md) を参照。既存の依存記録は自動で置き換えないため、Rustを検索する前に依存情報を読み直す。

未対応項目と開発上の課題は[開発課題](roadmap.md)、検証方法と技術構成は[開発者向け資料](development.md)を参照してください。
