# 実装済みの機能と対応範囲

2026-10-26時点の実装。初めて使う方は[README](../../README.md)と[マニュアル](../manual/README.md)を参照してください。ここでは検出・読み取り・照会の詳しい挙動を説明します。将来の設計案の全項目が実装済みという意味ではありません。

- 多言語のmanifestと配置設定を使った静的な候補検出。Node.js系、Python、PHP、Go、Rustなど。
- Vue・Next.jsなどの依存宣言による構成ラベル（Electron・Tauri・Remotion・Vite・Express・Hono・Expo・Django・FastAPI・Railsなどを含む）、Lambdaなどの静的な配置設定の識別。
- Xcodeプロジェクト（`*.xcodeproj`・`*.xcworkspace`・`Podfile`）、WordPressプラグイン（直下のPHPファイルの `Plugin Name:` ヘッダー。最大20ファイルの先頭8KBだけ読む）、`manifest.json` によるChrome拡張・Obsidianプラグイン・Zendeskテーマ、AWS Amplify・SST・Chaliceの設定。探索が完了すると、登録済みアプリの技術構成も新しい判定で更新する。
- AWS SAM: `template.yaml` / `template.yml` / `template.json` と、`sam-template.*`・`template-*`・`*.template.*`・`cloudformation*` の名前のテンプレート（`AWS::Serverless::Function` や Transform の宣言。AWSの宣言がないものは候補にしない）、および `samconfig.toml`（あれば `template_file` / `template` が指すテンプレートも読む）。クラウド上のスタック実在は確認しない。`.aws-sam` のビルド成果物は探索しない。
- 明示されたworkspaceの親子候補のグルーピング。独立したネストGitは統合しない。
- Git・SAM/CloudFormationテンプレート・Flutter/Dart・Docker・WordPress・Apps Scriptのフォルダを境界とし、配下で見つかった構成を1つのプロジェクトのComponentにまとめる。ネストGitだけは別候補。直下が `.git` だけのGitリポジトリは複数のアプリの入れ物とみなし、それ自体は候補にせず中のアプリを個別の候補にする（根拠に所属リポジトリを記録）。
- WordPress本体のないバックアップ（`wp-content` を含むフォルダ、`themes`・`plugins` を直接置いたフォルダ、`plugins/index.php` のあるフォルダ）も、サイト・バックアップ単位の1件にまとめる。探索結果には、配下で別に登録済みのプロジェクト数を表示する。
- WordPressのコア（wp-includes / wp-admin）・uploads・プラグインやテーマの内部、`*.dist-info` を含むPythonライブラリの同梱先（Lambdaレイヤーなど）は探索しない。
- 新しい探索は、深さ・総件数・総時間による打ち切りをせず、進捗・処理待ち・検出根拠をSQLiteに保存する。フォルダ一覧は少量ずつ読み、候補の整理も保存しながら進める。
- 既定の生成物・取得済み依存、ユーザー指定フォルダ、symlinkの除外は維持する。探索中は確認項目・処理済み/処理待ちフォルダ・検出数を表示する。全体量は不明なので完了率を表示しない。他画面に移っても探索は続く。
- 候補は、登録した探索フォルダごとの最新の探索結果を1つの一覧にまとめて表示し、そこから選んで登録する。同じパスの候補は新しい探索の結果を1件だけ示す。「すべて探索」は登録した探索フォルダを1つずつ順に探索し（同時には実行しない）、見つからないか除外されたフォルダは飛ばす。途中で一時停止・キャンセルすると残りは探索しない。進み具合はサーバーのメモリに持ち、再起動後は探索済みのフォルダの結果だけが残る。
- 「一時停止」「続きから再開」「失敗したフォルダを再試行」に対応。アプリ再起動時は保存済み探索を一時停止に復旧し、自動では再開しない。「保存した探索の履歴」から過去の探索も開ける。探索記録の削除は登録済みプロジェクトに影響しない。
- 候補は30件、問題は100件、履歴は20件ずつ取得する。候補の一括登録は1回2000件までで、探索件数の上限とは別。大きなプロジェクトの一覧は構成と根拠を各200件までと総数を示し、登録時は保存済みの全構成を使用する。[設計と検証記録](../design/discovery-plan.md)を参照。
- 選択登録、重複防止、登録直前の構成再確認、検索・絞り込み、用途・タグ・状態・メモの保存。
- アーカイブ・復帰、整理履歴、別タブの編集競合の検出、未保存の入力保護。
- 明るい管理画面、システムフォント、最小限の動き、⌘Kでの検索、狭いウィンドウへの対応。
- 依存版台帳と横断検索（npm・Yarn・pnpm・Composer・Python・Rust・Go・Ruby・Maven）。「アプリを追加」で登録したプロジェクトは、登録後に自動で依存情報を読み取る（裏側で順に読み、画面に進み具合を表示）。登録済みのプロジェクトは「依存検索」の「アーカイブ以外をすべて読み取る」でまとめて読める。カタログで選んだプロジェクト（1回1000件まで）またはプロジェクト詳細から「依存情報を読む」と、プロジェクト直下と各Componentの lock を読み、パッケージ名・解決版・宣言範囲・直接/間接・本番/開発・取得元を保存する。「依存検索」の1つの入力欄に、パッケージ名（部分一致・大文字小文字を区別しない）を入れて、使っているプロジェクトを探せる。`名前@版` と書くと版（完全一致）でも絞る。完全一致の検索は、記録されているパッケージの一覧から名前を選んで行う。
  - 読む lock：`npm-shrinkwrap.json`／`package-lock.json`（lockfileVersion 1〜3）、`yarn.lock`（v1・2以降）、`pnpm-lock.yaml`（lockfileVersion 5〜9）、`composer.lock`、`poetry.lock`、`uv.lock`、`Pipfile.lock`、`requirements*.txt`、`Cargo.lock`、`go.mod`、`Gemfile.lock`、`pom.xml`。1つの場所に複数ある場合はすべて読む。workspace（npm・Yarn・pnpm・uv・Cargo）のメンバーは外側の lock で読む。
  - `requirements*.txt` は `==`（`===`）で版を固定した行だけ版を記録する。範囲指定や版のない行は宣言だけを残し、照会しない（画面に「版の固定なしを含む」と件数を出す）。`-r` の参照先はたどらず、同じ場所の `requirements*.txt` をそれぞれ読む。推移的な依存は書かれていない分しかわからない。
  - Python のパッケージ名は PEP 503 の形（小文字、`_`・`.` を `-`）で記録し、検索も同じ形で一致させる。Composer の `v1.2.3` は `1.2.3` として記録する。
  - Yarn 2以降・pnpm の lock はレジストリを記録しないため、取得元は「レジストリ（lockに記録なし）」になる。Composer は Packagist の記録（`notification-url`）があるものを公開、VCS・path のリポジトリのものを Git・ローカルとして扱う。
  - pyproject.toml がツールの設定だけ（ruff など）のときは Python のプロジェクトとして扱わない。setup.py は読まない。
  - `go.mod` は Go 1.17 以降なら間接依存も記載されるため、そのまま読む。それより前の `go.mod` は「直接依存のみ」と表示する。`Gemfile.lock` は Gemfile（Rubyのコード）を評価しないため、本番/開発の区別は「不明」になる。`pom.xml` は直接依存だけを読み、プロジェクト内の親POMのプロパティと `dependencyManagement` を反映する。推移的な依存は照会しない（「直接依存のみ」と表示）。詳細は [依存解析の対応範囲](dependency-coverage.md)。
  - 「依存検索」の下に、記録されているパッケージを使っているプロジェクトが多い順に一覧する（直接依存として使う件数・記録された版つき）。検索すると、検索した文字を名前に含むパッケージに絞られる。名前を選ぶと、その名前だけ（完全一致）で検索する。
  - lockを読むだけで、対象プロジェクトでのインストール・スクリプト実行・設定の評価はしない。読み直すとそのプロジェクトの結果を置き換える。詳細画面では、読み取り後にlockや宣言のファイル（package.json・composer.json・pyproject.toml・Pipfile・Cargo.toml・Gemfile・親POM）が変わったことを示す。
  - lockなし・壊れたlock・未対応の形式・宣言のファイルとの不一致・読み取れないファイル（シンボリックリンクや範囲外への参照、32MiB超）は、それぞれ区別して表示する。読めたlockと未対応形式が同居する場合は「一部を読み取れません」とし、全体を確認できたとは扱わない。lockなしの場所だけがあっても要対応には出さない（権限不足や壊れた形式など、本当に読めなかったときだけ要対応）。読み取っていないプロジェクトは検索結果に含まれず、画面に読み取り済みの件数を示す。
  - 解決版はlockに記録された版で、node_modulesの実体やデプロイ済みの版を確認したものではない。公開レジストリ（registry.npmjs.org・registry.yarnpkg.com・packagist.org・pypi.org）以外のレジストリ・URL・Git・ローカルの依存は区別して記録する。
- 対応記録（メニュー「脆弱性と対応」）。照会で見つかった既知の脆弱性を、プロジェクト×アドバイザリの単位で対応状況（未対応・調査中・対応中・再照会待ち・対象外）を記録して進める。アーカイブしたプロジェクトは一覧に出さない（対応記録は残る。詳細の対策メモではそのプロジェクトだけ参照できる）。「解消確認」は手では付けられず、再照会で検出されなくなったときに自動で付く（再び検出されたら未対応に戻る。一部しか照会できなかったときは何も変えない）。対象外には根拠が必要で、見直す日を入れられる。
  - 優先度は悪意のあるパッケージ・緊急・高を「高」、中を「中」、低を「低」、重大度不明を「要確認」とする。公開状況・管理状態・dev/間接依存という分類だけでは自動で下げない。出典・CVSS値・差異・前回情報の保持を画面とメモに示す。アーカイブは通常の対応一覧から外れるが、詳細と記録は残る。判定範囲と取り込みの制限は [重大度と優先度](severity-policy.md) を参照。
  - プロジェクトごと・アドバイザリごとに切り替えて、状態・優先度・公開状況・文字で絞り込み、まとめて状態を変更できる（1回800件ずつ送る）。
  - 詳細の上部に「プロジェクト全体の対応状況」を1か所表示する。個別記録を集約し、未対応が残る場合は未対応、全件解消を完全な再チェックで確認した場合は完了となる。一括変更はその時点の全対象を1回で保存し、通常の変更では個別メモを保持する。対象外にする場合は共通の根拠が必要。対象が変わっていた場合は変更を保存せず再確認を促す。個々の脆弱性の詳細には対応状況の変更ボタンを置かない。
  - 「対策メモ」で、未解消のものをパッケージの版ごとにまとめた Markdown を作り、コピーできる（直接依存は更新先の版、間接依存は `npm ls`・`yarn why`・`pnpm why`・`composer why`・`uv tree --invert`・`poetry show --why`・`go mod why -m`・`mvn dependency:tree` などでの経路確認、依存管理方針に沿った進め方、確認していないことを含む）。
- 既知の脆弱性の照会（npm・Composer（Packagist）・Python（PyPI）・Rust（crates.io）・Go・Ruby（RubyGems）・Maven、[OSV](https://osv.dev)）。依存を読み取ったプロジェクトを一覧で選ぶか詳細画面から「脆弱性を照会」すると、確認画面で送信先（`https://api.osv.dev`）と送る件数を示してから照会する。
  - 送るのは ecosystem・パッケージ名・版だけ。npm・Composer・Python・Ruby・Go・Mavenは公開レジストリと別のレジストリ（ミラー・社内のインデックスなど）由来の依存が対象（Go・Mavenは取得元が記録されないため、非公開のモジュール名も送られる）。Rustは公開crates.io由来を確認できた依存だけが対象で、パス・プロジェクト名・ソース・Git/URL/ローカルの依存は送らない。同じ版は1回だけ照会する。
  - 結果は照会したときの依存台帳に結びつけて保存する。アドバイザリのID・別名・概要・重大度（発行元のラベル、CVSS v3.0/v3.1/v4.0 の点数、悪意のあるパッケージ）・該当範囲の修正版（アドバイザリに記載がある場合）を、一覧・詳細・カタログ上部に表示する。取り下げられたアドバイザリと、別名による重複は数えない。
  - 一度に1000件まで選べる（フォルダ別表示のフォルダのチェックでまとめて選べる）。照会は裏側で進み、画面上部に「依存を読み取り中 → OSVに照会中 → 詳細を取得中」の進み具合を出す。照会の前に、依存を未読み取りのもの・前回lockがなかったり一部しか読めなかったもの・読み取り後にlockが変わったものを読み直し、判定できるものはすべて判定する。lockがないなど判定できないものは「判定できる依存なし」と示し、「脆弱性なし」とは記録しない。
  - OSVへは500件ずつ順に送り、詳細は8件ずつ並行して取得する。混雑（429）・サーバーエラー・応答なしは、`Retry-After` があればそれに従い、なければ1秒・2秒・4秒・8秒と待って再試行する（最大4回）。
  - 照会に失敗した分は「0件」にせず、前回の結果を残す。照会後に依存内容・検査範囲が変わると「再チェックが必要」と表示する。同じ内容を読み直しただけでは前回の結果を維持し、照会日時は更新しない。古い記録は照会時の内容を特定できる場合だけ引き継ぐ。既知の脆弱性があるプロジェクトは「要対応」に入る。
  - OSVに登録済みの既知の脆弱性だけが対象で、実際に悪用できるか・未公開の問題がないかはわからない。
- osv-scanner の併用（任意。設定で「osv-scannerを使う」を選んだときだけ）。owndappが読めない lock（`Package.resolved`・`pubspec.lock`・`gradle.lockfile`・`packages.lock.json`・`packages.config`・`*.csproj`・`bun.lock`・`mix.lock`）を1件ずつ、詳細画面で結び付けた手元のDockerイメージを `docker save` で書き出して照会する。結果は同じ照会結果・対応記録に入り、「osv-scanner: ファイル名／イメージ名」と由来を表示する。未対応のファイルとイメージをすべて照会できれば照会結果を「完了」にでき（`Package.swift`・`build.gradle` は隣の lock で照会済みとみなす）、どれかが失敗すれば「一部のみ」にして解消扱いにしない。OSパッケージ（Debian・Ubuntu・Alpineなど）の修正版は、版の並びを判定せずアドバイザリの記載をそのまま示す。osv-scanner は owndapp がインストールしない。
- Git情報の読み取り（詳細画面、カタログで選んで「Git情報を読む」、またはカタログの「Gitをすべて読む」でアーカイブ以外を一括）。プロジェクト直上または祖先の `.git`（worktree の `gitdir:` 含む）から、現在ブランチ（または detached）と remote 名／URL を読む。URL の認証情報は保存前に除く。fetch・pull・`git status`（未コミットや追跡先との差）はしない。読み取りはこのMacの中だけで、外部には送らない。一括は裏側で進み、画面上部に進み具合を出す。

「依存検索」の「依存の検索範囲」で、未読・未対応形式・一部読取失敗・lockなしのアプリを確認できる。名前・パスで絞り、表示中のアプリだけを選んで依存情報を読み直す。アーカイブは「アーカイブも含める」を選ぶと対象にできる。読み直すと検索結果と記録パッケージを更新する。

Rust・Go・Ruby・Mavenの取り込み・検索対象と未対応範囲は [依存解析の対応範囲](dependency-coverage.md) を参照。既存の依存記録は自動で置き換えないため、これらを検索する前に依存情報を読み直す。

未対応項目と開発上の課題は[開発課題](../design/roadmap.md)、検証方法と技術構成は[開発者向け資料](development.md)を参照してください。

## 画面ごとの詳しい動き

利用者向けの手順は[マニュアル](../manual/README.md)にある。ここには、旧 `usage.md` にあった画面ごとの細かい条件・上限・判定を残す。

「依存検索」はメインメニューから直接開けます。入力欄は「パッケージ名」の1つだけです。名前の一部で探し（大文字・小文字は区別しない）、`Brotli` から `brotli-wasm` なども見つかります。版でも絞るときは `next@15.1.0` のように `@` のあとに版を書きます（版は完全一致）。検索すると、下の「記録されているパッケージ」もその文字を含む名前に絞られ、名前を選ぶとその名前だけ（完全一致）で検索します。「依存の検索範囲」の「アプリ名・パスで絞り込み」は、読み直すアプリを探すための欄で、パッケージは検索しません。検索範囲は読み取り済みのlock内で、コード全体やOS標準機能の利用は検索しません。

メニューは「ホーム」「アプリを追加」「登録したアプリ」「脆弱性と対応」「依存検索」「設定・使い方」の6項目。初回はホームからフォルダを追加し、候補を選んで登録します。登録後は脆弱性チェックを案内し、送信内容の確認後に「脆弱性と対応」で優先度の高いものから対応します。用途・タグの入力は任意です。

「登録したアプリ」の中で利用中／アーカイブを切り替えます。「一覧／フォルダ別」で保存場所の階層を参照でき、フォルダ単位での選択も維持します。「設定・使い方」にインストールから整理までの6段階のガイドがあります。


1. 「アプリを追加」の「フォルダを追加」で、macOSのフォルダ選択ダイアログ（Finder）から親フォルダを選ぶ。Windowsでも標準ダイアログから選択でき、「探索フォルダをパスで追加」へ直接入力もできる（例: `C:\Users\名前\Projects`）。選んだフォルダは探索フォルダとして登録され、すぐに探索を始める。「探索フォルダをパスで追加」から直接入力もできる（絶対パス、または `~/Projects` 形式。Windowsは `~\Projects` も使用可。スペースを含むパスもそのまま入力する）。登録した探索フォルダは一覧に並び、最後の探索の日時・結果・候補数（未登録の数）を示す。候補は、登録したすべての探索フォルダの最新の結果を1つの一覧にまとめて表示する（入れ子のフォルダで同じプロジェクトが見つかっても1件）。「すべて探索」で登録したフォルダを順に探索し直し、各フォルダの「再探索」で1つだけ探索し直せる。探索中に一時停止・キャンセルすると、残りのフォルダは探索しない。最後の探索が完了していないフォルダは「詳細」から問題の確認・再開・再試行ができる。×で登録を解除しても、登録済みのプロジェクトは変わらない。これまでに探索したフォルダは、初回に自動で一覧に入る。
   探索したくないフォルダは「除外するフォルダを追加」か候補の「除外」で指定する。「除外フォルダをパスで追加」から直接入力もできる。そのフォルダとサブフォルダは以後の探索で読み取らず、表示中の結果からもすぐ消える。一覧の×で解除できる。
2. 根拠と構成を確認し、登録する候補を選択する。「表示中の新規候補をすべて選択」で、絞り込み・検索に一致する新規候補をページをまたいでまとめて選べる（1回の登録は2000件まで）。
3. 追加分の一覧から「登録したアプリの脆弱性をチェック」へ進む。用途・タグ・管理状態・メモの入力は任意で、必要な場合に詳細で記録できる。用途が空なら、登録後にプロジェクト直下のREADME（見出し・バッジ・画像・コード・HTMLを除いた最初の説明の段落、最大200字）から自動で入れる。READMEがない、または生成ツールのテンプレートのままなら、package.json・composer.json・pyproject.toml・Cargo.toml・pubspec.yaml の description を使う。抜き出しはこのMacの中だけで行い、外部には送らない。自動で入れた用途には「README.mdから自動入力しました」と表示し、編集すると自分の記述として扱う。書いた用途は上書きしない。登録済みのプロジェクトは「脆弱性と対応」の「READMEから用途を入れる」でまとめて入れられ、詳細画面では用途が空のときに候補を表示する（ボタンを押したときだけ入れる）。管理状態は 未設定（登録直後）・計画中・開発中・テスト・検証・運用中・保留・完了・中止・アーカイブ。
4. 探索が完了すると、同じ場所に登録済みのアプリの技術構成と検出の根拠も、そのときの判定で更新する（名前・用途・タグ・メモ・管理状態・公開状況は変えない）。判定のルールが改善されたあとは「アプリを追加」の「すべて探索」で反映できる。 「登録したアプリ」は「利用中・アーカイブ・すべて」で表示を切り替える。検索・技術・管理状態・Gitの絞り込み、件数、「一覧／フォルダ別」は1段にまとめてある。パスは末尾の2階層だけを表示し、全体はマウスを重ねると確認できる。カタログは「一覧」と「フォルダ別」を切り替えられる（選んだ表示はブラウザに記憶する）。フォルダ別表示はフォルダの階層で折りたたみ、別のプロジェクトの中にあるプロジェクトはその子として表示する。中身が1つだけのフォルダは `vue/dev` のようにまとめる。フォルダごとに件数・要対応・既知の脆弱性があるプロジェクトの数を示し、フォルダのチェックで中のプロジェクトをまとめて選べる。一括操作（タグ・管理状態・依存情報・脆弱性照会）は1回1000件まで。検索・絞り込み中はすべて開いて表示する。
   名前・パス・技術・用途・タグ・メモで検索する。一覧で選んだプロジェクトに、タグの一括追加と管理状態の一括変更ができる（アーカイブにする場合は共通の理由を入力できる。任意）。
5. 初回ホーム、または「設定・使い方」でエディタとターミナルを任意で1つずつ登録すると（macOSは.app、Windowsは[対応する.exe](windows.md)を選ぶ）、一覧の各行と詳細画面の「○○で開く」で、プロジェクトのフォルダをそのアプリで開ける。
   macOSでは一覧の各行と詳細画面の「Finderで表示」で、プロジェクトのフォルダを選択した状態のFinderを開ける。
6. フォルダを移動・削除した場合、カタログを開くたび（または「存在を再確認」）に「フォルダが見つかりません」と表示する（「存在を再確認」と「Gitをすべて読む」は、一覧の絞り込みの右にある「⋯」の中にある）。一覧上部の「カタログから外す…」で、確認のうえまとめて外せる。外す直前にも再確認し、フォルダが存在するものは外さない。外したプロジェクトの用途・タグ・メモ・履歴は記録に残す。移動先で使う場合は「アプリを追加」から登録し直す。
7. 登録済みアプリから探索除外するときは、同じフォルダ内の登録済みアプリもカタログから外すか選べる（既定は外さない）。除外設定のフォルダにある登録済みプロジェクトは、カタログで「除外設定のフォルダにあります」と表示する。一覧上部の「カタログから外す…」（または詳細画面）で、確認のうえ外せる。外す直前にも除外設定を再確認する。記録は残る。
8. アーカイブは詳細画面の「アーカイブする」チェックボックスで行い、理由を記録できる（理由は任意。管理状態のプルダウンには出さない。一覧の一括変更ではアーカイブも選べる）。アーカイブ中は管理状態を変更できず、チェックを外すとアーカイブする直前の管理状態に戻る。

### 依存検索の確認範囲

検索対象は、最後に読み取った依存の記録です。「依存の検索範囲」で未読・未対応・一部読取失敗・lockなしを確認し、対象を選んで読み直せます。アーカイブしたアプリも明示的に含められます。手順と対象形式は[依存解析の対応範囲](dependency-coverage.md)を参照してください。

停止・更新・バックアップは[運用ガイド](operations.md)、対応状況の扱いは[プロジェクトの対応状況](project-response.md)を参照してください。

登録したアプリは「脆弱性診断可能」と「診断対象外」に分けて数えます。脆弱性診断可能は、最後に読み取った依存にOSVへ照会できるもの（公開レジストリの版付きの依存）が1件以上あるアプリです。依存をまだ読み取っていないアプリも、チェック時に読み取るため診断可能に含めます。診断対象外は、lockなし・依存解析が未対応の形式（Swiftなど）・Gitやローカル参照の依存のみなど、照会できる依存がないアプリです。診断対象外は「脆弱性なし」とは判定せず、チェック済み・未チェックの数にも含めません。lockを追加したあとは依存情報を読み直すと診断可能に移ります。「登録したアプリ」の集計は 脆弱性診断可能 → チェック済み → 既知の脆弱性あり の順に、前の数の内訳です。未対応の形式は「要対応」の読み取り失敗・要再確認には数えません。要対応に入るのは、対応する形式のファイルが読めない場合と、照会や詳細取得が失敗した場合です。npmとSwiftのように対応形式と未対応形式が同居するアプリは、照会結果を「一部のみ」として記録し、既知の脆弱性を自動で解消扱いにはしません。

osv-scanner（`brew install osv-scanner` などで導入）がある場合は、「設定・使い方」で「osv-scannerを使う」を選ぶと、Swift・Dart・.NET・Gradle・Bun・Elixir の lock と Docker イメージもチェックできます。イメージはアプリの詳細の「コンテナイメージ」で、手元のイメージから選んで結び付けます。照会の前の確認画面に、osv-scanner で照会するファイルとイメージが表示されます。

再照会時は、対象の依存情報を毎回自動で読み直してからOSVへ照会します。「依存情報を読む」を先に操作する必要はありません。フォルダが消えた・読み直し処理が失敗した場合は、古い依存で照会せず前回の結果を保持します。lockファイルの一部だけ読めた場合は、その範囲の判定となります。

照会・依存情報・Git情報・フォルダ探索の進捗は、画面上部中央の固定通知に表示します。スクロール中も確認でき、完了結果やエラーも同じ場所に表示します。完了通知は×で閉じられます。
