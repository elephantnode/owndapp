# 詳細画面のプロジェクト単位の対応状況

詳細画面では、ヘッダー直下の「プロジェクト全体の対応状況」で確認・変更する。脆弱性の詳細一覧には、個別の対応状況や変更ボタンを置かない。既存の個別対応記録は保持し、「脆弱性と対応」の記録と整合させる。

## 状態の集約

同じアドバイザリIDは1件として数える。未対応が1件でもあればプロジェクト全体は未対応。それ以外は対応中、調査中、確認待ち、対象外、解消確認の順で全体の状態を表す。状態別の件数も添える。

全件解消を完全な再チェックで確認した場合だけ「完了」とする。結果が古い、または照会が不完全な場合は、完了や対応不要と断定しない。0件は解消確認とは区別して「検出なし（照会済みの範囲）」と表示する。未照会は未照会と表示する。新たな未対応が見つかれば全体の状態も未対応になる。

## 変更

「プロジェクトの対応状況を変更」は、最新の記録にある全対象へ一括適用する。解消確認済みのみの過去の記録は変更しない。「完了」は選択できない。

通常の変更では個別メモを保持する。対象外にするときだけ全体に共通する根拠を必須とし、個別メモを共通の根拠に置き換えることを画面に明示する。対象外の見直す日は任意。それまでの対応履歴は保持する。

APIはPOST /api/projects/:id/response。画面が取得した対象ID集合と現在の照会結果を照合し、一致しなければ409で何も変更しない。一致した場合は全対象を1回のトランザクションで保存し、途中までの保存を防ぐ。既存の個別/選択変更APIの挙動は維持する。DBの形式や既存データの移行は不要。

取得エラーと保存後の表示更新エラーを区別し、再取得できる。照会を実行したり、実プロジェクトの依存を変更したりする機能は追加しない。

## 検証

Node.js 24.14.0で全171テスト、ブラウザ11件、型検査・ビルドが合格。複数脆弱性でも操作は1つ、全体更新、個別メモ保持、他プロジェクト不変、対象変更時の409、手動完了拒否、対象外の共通根拠、部分/古い照会、保存後の再取得失敗、390pxの表示を確認。全体更新の実APIはメモリDB、ブラウザ操作は架空データ専用の別DBを使用した。
